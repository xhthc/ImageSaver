# Runtime architecture and contracts

This is a navigation guide to the current source, not a future rewrite blueprint. It describes component boundaries and contracts implemented in the current source.

UI labels quoted here use English translations; the current product UI remains Russian.

The manifest uses classic scripts for the service worker and the content scripts, a zero-build runtime for them (they load as written), and the existing `offscreen` permission. All four download-start paths (direct, emergency fallback, X animation and Reddit animation) explicitly pass `saveAs: false`. The Saving controller and panel no longer expose or persist `askEveryTime`; legacy stored values are ignored without rewriting other preferences. Single and batch saves share the existing Downloads-relative folder routing.

The only build is the UI-only one in `ui/` (UX-08); its committed output in `popup/` is loaded as it is, so loading the unpacked extension or a package needs no Node and no build. Inspect the manifest before adding APIs; a planned feature does not alter the current permission set.

## Interaction and media flow

A pressed player wrapper can own a contained video omitted from the hit stack by pointer-event handling. Shared capture examines its descendant videos (at most 24 accepted; a larger list is refused), requires the gesture point inside exactly one video and retains the overlay-area and extra-point ambiguity checks. It never promotes descendant images or broad post containers. The captured media WeakRef, owner chain, source and point are re-proved at save time; a URL-less player's raw source must also remain unchanged. This uses a scoped DOM query, not a page-wide scan, and sends no media request.

On X, Shift+right-click is the explicit browser-menu path. The X content script stops propagation only after it has confirmed media, while leaving `preventDefault()` untouched; this keeps Chrome's native menu and prevents the site's parallel media menu from reopening or replacing the selected target. Shift+right-click on text or blank space keeps normal page behavior.

A user gesture supplies media evidence. Content scripts resolve the owning item when required. The service worker normalizes descriptors, creates and ranks candidates, applies the relevant ownership and transport-specific checks, and starts one download for the selected result.

Search source symbols rather than old report line numbers. Useful entry points include `resolveMediaTarget`, `executeMediaPlan`, `verifyFinalMediaMime`, `acquireOffscreenTask`, `transferOffscreenTask`, and `releaseOffscreenTask`. Provider helpers and tests define their current signatures.

Ownership precedes quality ranking. Current verification strength depends on the path:

| Path | Current evidence |
|---|---|
| Direct images | `probeCandidate` uses HTTP headers through HEAD or a limited GET fallback; candidate admission can use MIME, filename, and size for ambiguous responses. The normal direct-image branch does not inspect image payload bytes before Chrome downloads the URL. Final image verification requires an image MIME. |
| Generic direct video | `probeVideoUrlDetails` normally uses response MIME and URL evidence; some extensionless ambiguous-MIME sources require an MP4 byte probe. Do not assume all direct videos are byte-checked. |
| X ordinary MP4 acquisition | The X-specific path adds bounded MP4 container-byte verification. |
| Protected fetch / generated GIF | Offscreen fetching inspects magic bytes; GIF encoding produces an owned Blob whose actual animation/container checks are covered separately. |

Where bytes are inspected, container evidence must agree with the expected type. Header-based acceptance is not byte verification. Preserve request signatures. Do not silently turn a failed video into an image or reuse a Blob from a different variant. Any stronger verification policy needs its own implementation and regression scope.

## Formats and GIF semantics

Native images, GIFs, and direct MP4/WebM retain their verified formats. Ordinary MP4 downloads preserve any source audio already present. Separate-track DASH/HLS muxing is outside the current direct-download contract.

Confirmed X `tweet_video` and Reddit `preview.redd.it/*.gif?format=mp4` animations use `convertMp4VideoToGif` through provider-specific wrappers. RedGIFs videos remain native video. Looping, autoplay, a blob URL, or silence alone does not establish an animation. For RedGIFs clips with provider-declared audio (`hasAudio: true`), `resolveMediaTarget` and `verifyFinalMediaMime` probe audio candidates in order (HD, then same-clip SD on 404/410). When a later same-clip variant verifies after an absent (404/410) predecessor, `verifyFinalMediaMime` makes that exact plan member the first variant, so the URL that downloads, its verified MIME and its file name belong together and the absent predecessor is not requested again. Authoritative failures (HTTP 401/403, rate limits, transport errors, a non-video answer) fail closed without silent downgrade. Absence-only fallback to the selected silent source applies only when all declared audio renditions are proven absent (404/410). Stale frame context (`FRAME_CHANGED`) aborts the save with zero downloads, preventing download of old silent files. Native Chromium audio playback verification remains pending.

The retired general format chooser, generic conversion worker, and old conversion-limits file are absent. Do not reintroduce them from a historical review.

Current `GIF_CONVERSION_LIMITS` in `offscreen.js`:

| Bound | Value |
|---|---|
| Source duration | 30 seconds |
| Frame count | 150 |
| Maximum output dimension | 640 pixels |
| Encoded output size | 15 MiB |
| Total conversion budget | 45 seconds |

These are implementation bounds, not universal quality or player-compatibility promises. Review source if they change. Failure stops conversion rather than silently truncating output or renaming MP4 bytes. Frame timing and looping require real-file verification for the relevant playback claim.

## Offscreen and download ownership

The offscreen document is created under reason `BLOBS`. Privileged actions include `FETCH_PROTECTED_BLOB`, `FETCH_GELBOORU_BLOB`, `REVOKE_BLOB_URL`, `CONVERT_X_TWEET_VIDEO_TO_GIF`, and `CONVERT_REDDIT_VIDEO_TO_GIF`.

Messages carry lightweight metadata and Blob URLs, not encoded media buffers. Probe/conversion task ownership transfers to the download; completion, interruption, early terminal events, and failures must clean up idempotently. Preserve the closing lock and reference counts.

Protected fetching uses separate header, inactivity, and total-body budgets. A progressing slow transfer and a stalled connection are different cases. Inspect the current constants and tests before changing budgets.

## Save feedback (UX-02 / UX-04)

`background.js` creates one operation (correlation ID) per user-initiated save in the two context-menu handlers and threads it through `executeMediaDownload`/`executeMediaPlan` and both GIF conversion wrappers. States: resolving, converting, saving, then exactly one of complete, interrupted, cancelled, failed. **Only a `chrome.downloads.onChanged` terminal state (or a post-restart `downloads.search` of the extension's own ID) produces complete**; a resolved plan, a finished conversion or a returned download ID leaves the operation in `saving`. The existing `onChanged` listener forwards terminal events; the tracker maps only IDs it was given, peeks `earlyTerminalDownloadStates` when an ID is attached, and ignores unknown, repeated and stale events. A recoverable primary failure followed by a successful emergency fallback continues the same operation (fallback evidence is a filename hint only).

Operations persist as an allowlisted record (site, source host/extension, state, type/size evidence, failure stage/category/code/numeric status) in `chrome.storage.session`: at most 20 records, terminal ones dropped after 24 hours, no URLs/paths/queries/Blob URLs/media. A restarted worker reconciles non-terminal records with the existing download IDs and never re-downloads. Notifications (`notifications` permission) fire once per finished operation; routine success notifications follow `notifySuccess` (default on, throttled), failures always notify and also stay in the popup list and a `!` badge. HTTP status is recorded only when the pipeline observed a numeric status. The popup and the full page requests records through `FEEDBACK_*` messages accepted only from extension pages; the report is built in the page from the allowlisted record and copied only on a click. Manual retry is not automated (stale signed URLs are not reused); the UI explains the manual path.

## Save history (UX-03)

`createTracker` offers every operation that reaches a terminal state (including states set by restart reconciliation) to `lib/feedback_history.js` through the `onFinished` hook. The store lives in `chrome.storage.local` (`imageSaverHistoryV1`), keeps at most 50 entries for 7 days, upserts by operation ID (repeated or post-restart events never duplicate) and serializes writes. Recording is **opt-in**: it requires `historyEnabled === true`; a missing, malformed or unreadable value never authorizes it, and disabling does not delete. `clear()` persists a `clearedAt` boundary in the same document in one write; an operation created at or before it is never recorded later (so a stale session record replayed by restart reconciliation cannot resurrect it), later operations are recorded, and a failed write rejects so nothing is reported as cleared. `prune()` removes expired/surplus entries from storage at worker start and on every `list()`/`record()`; a failed cleanup is surfaced as `pruneFailed` and never blocks saving. Entries are the allowlisted UX-02 records plus `postUrl`, accepted only through `safePostUrl` (https X status pages, canonicalised; the X handler passes the post of the selected media). History messages (`HISTORY_LIST`, `HISTORY_CLEAR`) are accepted only from extension pages. A history write failure never affects a download, notification or the session-storage tracker. The full-page history controller is `ui/src/core/history.js`; React components in `ui/src/components/app/` render text nodes, open links with `rel="noopener noreferrer"`, copy on click only and report clipboard or clear failures truthfully. `popup/` contains the committed build output.

### File names in results (UX-03)

Records carry `filename` (a bounded basename, `FB.safeBasename`: URL/Blob/data input rejected whole before any truncation or segment extraction, Windows drive/UNC/POSIX paths reduced to the basename, control/bidi characters neutralised, extension kept, 120 characters) and `filenameKind` (`intended` | `actual`). The requested name is recorded as `intended` when the download ID is attached (the converted GIF's own name for X/Reddit conversion, the fallback's own name for an emergency fallback, which resets the primary name). `actual` is set only from `DownloadItem.filename` of the extension-owned ID (terminal event, early-event/attach lookup, restart reconciliation) because Chrome may rename on collision or Save As; interrupted or filename-less items stay `intended`. Rows show the name as the main text with result/site/type/time as secondary text; legacy records and failures before naming keep the previous summary. Names are not part of notifications or the bug report.

## Organized UI (UX-05, rebuilt with shadcn/ui in UX-08)

### Build and layering (UX-08)

`ui/` is a UI-only development build: `npm ci` and `npm run build` in `ui/` (Vite with Rolldown, React 19, Tailwind CSS v4, Radix UI through the shadcn/ui component sources, Lucide icons) write `popup/quick.html`, `popup/popup.html` and `popup/assets/*` plus `popup/THIRD_PARTY_NOTICES.txt`. The output is committed, so the extension and every test package load without a build; `npm run check:built` rebuilds into a temporary folder and fails when the committed `popup/` differs. The build touches nothing else: `background.js`, the content scripts and `offscreen.js` are unchanged and independent. The pages use only local modules, scripts and styles with the default MV3 extension CSP (no inline script, no eval, no remote code, no new permission). Two Skiper UI free components are used with attribution: "Custom tooltip" (`ui/src/components/skiper/tooltip.tsx`) and "Progressive Blur" (`progressive-blur.tsx`); their licence statement and every bundled dependency's licence are in `popup/THIRD_PARTY_NOTICES.txt` (generated by `node ui/scripts/gen-notices.mjs` from the bundler's source maps) and the page footer links to it.

Behavior lives in controllers without React or DOM (`ui/src/core`): `createQuick` (compact popup: the history opt-in, invitation and dismissal, the superseded-mount counter, `storage.onChanged`, the gear), `createFeedbackList` (recent results: load and sanitize through `ImageSaverFeedback.sanitizeRecord`, unread failures, acknowledgement only for a current mount whose list is visible, clear, deep link), `createHistory` (opt-in preference, retained records, clear), `createSettings` (the seven Saving/Embed keys, the folder rules of `lib/folder_path.js`, the immediate `notifySuccess` preference), `nav` (sections, URLs) and `present` (row texts, report text, statistics view). UX-06: `core/keys.js` holds the storage keys and `watchStorage`; `createFeedbackList` and `createHistory` each take one `chrome.storage.onChanged` subscription (session/local `imageSaverFeedbackV1`; local `imageSaverHistoryV1` and `historyEnabled`) that is only a trigger: the data is requested again through the existing `FEEDBACK_LIST`/`HISTORY_LIST` messages, serialized with a coalescing dirty flag (no parallel requests, no timers, no polling), unread marks are kept as a union, acknowledgement still requires a current, visible mount, and `dispose()` removes the subscription so a closed page makes no more requests. React components subscribe to their stores (`useSyncExternalStore`) and render text nodes only; there is no HTML injection. The controllers are tested in Node (`test_ux_ui.js`, `test_ux_feedback.js`, `test_suite.js`), the components in jsdom (`test_ui_render.js`).

### Compact popup and full page

`manifest.json` `action.default_popup` is `popup/quick.html`: `QuickApp` renders the five newest session results (no preference control; an expanded result offers "Open on history page" for `popup/popup.html?op=<id>#history`), and the header gear (`#openSettingsButton`, `aria-label` and tooltip "Settings") calls `chrome.tabs.create` for `popup/popup.html#saving` (no extra permission) on an explicit click, closing the popup only after the tab opened. The list is mounted only while `historyEnabled === true` (missing, malformed or unreadable means disabled; nothing is shown before the preferences were read); otherwise a small invitation ("Enable history" writes only `historyEnabled`; "Dismiss" writes only `historyInviteDismissed`) is shown unless dismissed, in which case only the header and gear remain. A failed write leaves the state unchanged and shows an alert; `storage.onChanged` applies preference changes while the popup is open; an older `storage.get` response never overwrites a value an event or a click set after the read began, and a superseded list mount neither renders nor acknowledges. Tracker, notifications, error badge and the full page do not depend on this presentation.

`popup/popup.html` is the full page, one page for all sections: notification clicks and result deep links open `popup.html?op=<id>#history` and the results list opens that operation and scrolls to it. `FullApp` renders a shadcn/Radix tab list over four panels (history and statistics, Saving, Notifications, Embed): Arrow/Home/End keys with roving focus, `hashchange`, `?op=` wins over `?section=`, then the hash, unknown values fall back to history. All panels stay mounted (the inactive ones hidden), so unsaved edits survive a tab switch; the results list in the History panel acknowledges unread failures (`FEEDBACK_MARK_SEEN`) only for a current mount while that panel is displayed, keeps them pending while it is hidden, acknowledges when the History tab is actually shown and retries a failed acknowledgement the next time. The shared "Save settings" bar is shown for Saving and Embed only; `notifySuccess` (a switch) and `historyEnabled` (a switch) are written only by their own controls and immediately, with a revert and a message when the write fails. The seven storage keys of the Saving/Embed settings, their defaults, the allow-lists and the folder rules are unchanged, so migration and lazy folder creation behave as before. `FB.computeStats` summarises the loaded history only: outcomes (success, failure/interruption, cancelled, unknown = lost Chrome record), types with an evidence split (verified vs filename hint, unknown stays unknown) and a size sum limited to measured sizes of successful saves with the coverage stated. No new store, telemetry or permission.

### Design system

The pages are dark (`<html class="dark">`, Russian labels) and keep the Image Saver slate/blue identity. shadcn/ui semantic tokens are defined in `ui/src/index.css` (checked: body text >= 7:1, secondary text and status colours >= 4.5:1, focus ring >= 3:1, in `test_ux_ui.js` section 30). State is never colour alone (icon plus text), controls have visible keyboard focus, motion is restrained and removed under `prefers-reduced-motion`, long file names are truncated in rows (full text in the tooltip and the accessible name) and wrapped in details.

## Copy-link UI

Each button copies the canonical link of its owning post/video. Original-platform hosts are the defaults; popup options and their user-authored order/labels are defined in source. Alternate preview links are constructed locally without requests to preview services.

Canonical-link construction, successful clipboard writing, and preview rendering by a messenger are separate outcomes. Fail visibly when ownership or clipboard delivery is unavailable; preserve native page controls.

## Release checks and manual installation

The full page adds an Updates tab (`#updates`) beside the existing settings. `ui/src/core/updates.js` owns the page-local controller; `UpdatesPanel` uses the existing store, tab, select and button components. Only activating that tab triggers an anonymous request to the fixed repository's GitHub Releases API, at most once every 24 hours; a manual check bypasses the cache. There are no alarms, background-worker changes, installation APIs, remote scripts or new permissions.

`imageSaverReleaseChannel` defaults to stable; beta also admits prereleases. `imageSaverReleaseCheckV1` stores release metadata and attempt/success times in local storage. Numeric one-to-four-component tags matching manifest versions, optionally with `v`, are compared component by component. Drafts, malformed tags and incompatible channel entries are ignored. The first 100 releases are inspected. Links are constructed for this repository from validated tags; response-supplied URLs, assets and release bodies are not used. Requests omit credentials/referrers, reject redirects and time out after 10 seconds. An error preserves the previous successful result and its timestamp, and is shown explicitly; storage failures are visible. Closing the page aborts its pending request. Media handling, save feedback and history remain independent.

Installation is manual: download the release ZIP, replace the existing unpacked directory's files at the same path and reload the extension. This flow does not download packages, rewrite extension files or call `runtime.reload`.

The anonymous API path requires a public repository; private repositories can return 404. There is no token input or automatic change to repository visibility. Before public publication, the checker displays the access failure and the user can open GitHub through their browser account.

## Future extension points

Resource/type folders are already implemented through `lib/folder_path.js` and `resolveDownloadPath` at the filename boundary: the default single-folder mode and optional site/type subfolders consume existing ownership and verified output metadata. Future per-resource preferences (SETTINGS-01) must reuse these rules, without rediscovering media or inferring output type solely from a suffix.

Planned Telegram actions should reuse selected-media resolution and add an explicit opt-in draft/delivery boundary. The normal saving path must remain usable without Telegram configuration. Decide Bot API capabilities, credentials, channel selection, file staging, scheduling executor, and acknowledgement/retry policy before runtime work.

Broader generic detection should reuse the existing pipeline after provider polishing. Keep adapters for first-party APIs, protected CDNs, and complex players where necessary. Structural module extraction remains the final, separately authorized roadmap stage.
